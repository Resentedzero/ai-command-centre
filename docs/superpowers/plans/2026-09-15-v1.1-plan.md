# V1.1 Architecture and Implementation Plan

**Status:** proposal for operator review. No production code has changed. Not committed.
**Date:** 2026-09-15. **Baseline:** V1 frozen at `24abbee`.
**Authority:** the frozen spec (`docs/superpowers/specs/2026-09-12-ai-command-centre-design.md`) wins over this plan. Every change below that touches the runtime is either inside what the spec already permits, or is written up as an architecture-change record in §15 for explicit approval.

**The finding in one paragraph.** V1 already has almost everything V1.1 needs underneath it. It has versioned Registry writes for Agents, Grants, Tasks and Workflows, with an HTTP API. It has per-Invocation governance: stops, Grant, Policy, Budget, Approval, Router and Compiler. It has immutable Artifacts with hash checks and provenance reads, an Agent Detail read model, and an SSE feed. The spec already names the autonomous pattern: an agentic loop of many Invocations inside one Run, whose "LLM output can determine the next Invocation, but only within the Run's fixed Task/budget/Agent scope" (§3d, Phase 11). What is missing:

1. One executor relaxation, so a model can end a bounded plan early.
2. Two generic Task kinds, so steps other than research and publish exist.
3. A way for a step to consume an earlier step's output.
4. Starting a Goal without waiting for it to finish.
5. A structured deliverable schema and a document renderer.
6. A Keeper that answers deterministically first and goes through a governed Run otherwise.
7. The operator UI for all of it.

There is no new engine, permission model, artifact model, event source or infrastructure.

## 1. Current relevant architecture

```
UI (web/, Next 16, DOM pixel world) --HTTP + SSE--> API (Fastify, loopback, request guards)
  -> Workflow Interpreter (linear graph, slot per step, deterministic)
     -> Task Instance -> Run (one per attempt; plan from Task Definition kind)
        -> Executor walks a FIXED-LENGTH plan by position (seqNo = index + 1)
           tool:  stops -> Grant -> binding trust -> Policy -> Budget(usd) -> [Approval] -> yield
           llm:   stops -> Router (tier, candidates, reserve, 1 fallback) -> Compiler -> yield
           det.:  runs inside the transaction
        -> dispatchAndRecord: pre-dispatch re-check tx -> provider/tool call (no tx) -> record tx
  -> Events (immutable, DB triggers) ; Artifacts (immutable, sha256) ; budget_counters
Postgres only. Claude subscription CLI adapter (`claude -p`, no tools, --json-schema) is the runtime path.
```

These are the load-bearing facts the design depends on. Each was verified in code.

## 3. Autonomous-loop design (the core of V1.1)

### 3.1 Placement

An autonomous agent does its work as **one Task Instance of a new Task Definition kind, `agent_objective`, run by one Run**. It is the spec's agentic loop. It composes like any step:

- **Delegating an objective:** a Goal whose Workflow Definition has one `agent_objective` step bound to the agent. The Goal's title and description *are* the objective; the Compiler already puts them in task state.
- **Inside a custom workflow:** any step can be `agent_objective`. For example, "Research until evidence is sufficient" is an autonomous step, not a graph loop.

The loop never creates Task Instances, never changes topology, and never calls a provider except through the Router. Every action is an ordinary Invocation, so it passes the same stop, Grant, Policy, Budget, Approval, Router, Compiler and event path as V1.

### 3.2 The bounded plan

The builder returns a plan whose **maximum length is fixed at build time** from the step's validated limits:

```
for k in 1..maxIterations:
  [k.decide]  LLM            intent decide_next_action -> DecisionV1 (structured output)
  [k.act]     deferred on k.decide's artifact:
                intent  -> LLM Invocation for that cognitive intent -> WorkResultV1
                tool    -> Tool Invocation via resolveToolInvocation (full governance chain)
                gate    -> Tool Invocation of the checkpoint capability (Approval, §5.4)
                refused -> deterministic Invocation recording why (not granted, over cap, invalid)
                finish  -> SKIP
  [k.record]  deterministic  writes ledger artifact v(k) + event agent_loop_iteration_recorded
                             (SKIP after finish)
[final.write]   LLM            intent write_deliverable -> DeliverableV1
[final.persist] deterministic  persists the `deliverable` Artifact with completion {status, reason}
```

**The one runtime relaxation (architecture-change record R1, §15).** A deferred position may resolve to `SKIP`:

- No Invocation is proposed, and the Executor moves on to the next position.
- `seqNo` stays equal to the position index, so gaps are allowed.
- The rule "a plan's length is fixed before the Run" still holds as an upper bound. What changes is that a model's recorded decision can make positions after `finish` never happen.
- It is deterministic. A SKIP depends only on persisted artifacts, plus a deadline check (§3.4) that is monotonic, so once exceeded it stays exceeded. Completed positions are never re-resolved.

The alternative is to let the plan grow one position per advance. That removes the build-time bound, so it is not recommended.

### 3.3 Decide, act, record

**`DecisionV1`** is the JSON Schema passed to the Router, so `--json-schema` enforces it on the CLI, and the builder validates it again deterministically for providers that don't:

```
{ assessment: string (<= 600 chars),
  done: boolean,
  action: { type: "intent" | "tool" | "gate" | "finish",
            intent?: one of step.loop.intents,
            capability?: one of step.loop.tools[].capability,
            input?: object (validated by that capability's loop-action schema),
            instruction?: string (<= 1000 chars),
            useArtifacts?: string[] (<= 4 ids; must be artifacts of this Run or the step's declared inputs) },
  ledgerNote: string (<= 280 chars) }
```

**Cognitive intents** (plan, brainstorm, research-synthesis, analyse, compare, write) are LLM Invocations. They are governed by Router, Budget, Compiler and stops. They are **not** Capabilities, because V1 applies Grants to actions with effects (tools), not to thinking. Which intents a step may use is a validated step parameter. See decision D2.

**Tool actions** need all of the following:

1. The capability is in `step.loop.tools` with a per-capability `maxCalls`. It is counted deterministically from this Run's prior Invocations.
2. The Agent version holds an unrevoked Grant. The builder pre-checks this read-only so an ungranted choice becomes a recorded `refused` action instead of failing the Run. Policy remains authoritative at the Invocation, so a Policy DENY still fails closed.
3. A **loop-action adapter** registered in that capability's module (`src/capabilities/<cap>/loopAction.ts`) maps the model's `input` to a `proposedActionSnapshot`. For `research.retrieve` that is `{query}`, length-bounded. **`amountOrScope` and `isNovelAction` are computed by code and never copied from model output.** A capability with no loop-action adapter cannot be chosen, which is how the loop never names a capability in core.

**Record** is a deterministic `agent_ledger` Artifact, a new immutable row per iteration. It holds `iteration`, action type and intent or capability, outcome status, result artifact id, the model's `ledgerNote`, and counter headroom read from `budget_counters`. The event `agent_loop_iteration_recorded` (additive, R4) carries the same fields minus the note text, so the SSE feed and trace can show the loop without reading artifacts.

### 3.4 Limits (bounded autonomy)

| Limit | Enforced by | Source of value |
|---|---|---|
| `maxIterations` | Plan length (structural) | Step parameter, ≤ operator cap (D4) |
| `maxRuntimeSeconds` | `k.decide` thunk: past `run.startedAt + limit`, remaining iterations SKIP and the final write runs with `completion: incomplete / deadline`. Checked only on decide positions (LLM, never resumed from approval), so resumes stay deterministic. Each CLI call is also bounded at 180 s. **Approval wait:** recommended to exclude time spent `awaiting_approval`, derived from the Run's `approval_required` and resolution events, so a gate a human answers hours later doesn't end the loop `incomplete`. Part of D4. | Step parameter, ≤ operator cap (D4) |
| Subscription tokens / `usd` | Existing Run, Task Instance and Day counters (reserve-before-call). A budget denial fails closed as today. **SHOULD:** the decide thunk reads headroom and routes to the final write before a call it cannot afford. | Existing ceilings. Loop-sized ceilings need a governance decision (D4) |
| Per-capability calls | Deterministic count in the act thunk | Step parameter |
| Allowed capabilities | Step allow-list **and** Grant **and** Policy (all three) | Step + Registry |
| Allowed intents | Step allow-list | Step parameter |
| Completion condition | Text in context for the decide step. The `done`/`finish` decision ends the loop; hitting the limits ends it `incomplete`. Model confidence is advisory (§10.4): the deliverable records *why* it ended. | Step parameter |
| Escalation | `gate` action: a checkpoint Tool Invocation that requires Approval, with the question and ledger hash in its snapshot. Approve continues the loop, reject fails the Invocation and the Run. **MUST:** `escalateWhen` text in context. | Step parameter + checkpoint Grant |
| Emergency stop | Already before every Invocation and pre-dispatch (`run`, `workflow_run`, `goal`, `agent_definition`, `capability_grant`, `global`) | Unchanged |

**Retries.** V1 retries a failed LLM Run by starting a new Run of the whole plan. For a loop that repeats every iteration. The shared Task Instance counter bounds the cost, but it is wasteful. Recommended: `agent_objective` opts out of automatic retry. A failed loop is a failed step, and its ledger stays inspectable. This is a retry-policy change, so it is decision D6.

### 3.5 Context per iteration (token efficiency)

Each decide call is compiled fresh by the existing Compiler. It contains:

- Tier 1: the agent's instructions, the objective (Goal), the step's loop parameters (intents, tools with calls remaining, completion and escalation text, iterations and deadline remaining), and the DecisionV1 instruction.
- Tier 2, in priority order: the **latest ledger artifact only** (compact; not the transcript), the previous act's result artifact, and up to 4 `useArtifacts` the model asked for last iteration.

History enters only as the deterministic ledger. Loop outputs are fenced as untrusted, because their `producingInvocationId` is non-null, which is correct. The Compiler records inclusions and exclusions (`context_compiled`), so context growth per iteration is measurable. `ceil(chars/4)` estimates remain a known approximation.

Act calls get only the instruction plus the named artifacts. The final write gets the ledger plus the result artifacts the final decision named.

Tier per call follows the agent's tier preference, which maps to the spec's `taskDifficulty` in the plan (§4.2). The Router is unchanged: the risk floor, escalation floor, performance-upward and budget fallback all still apply.

### 3.6 Side effects worth naming

- **Conditional Autonomy becomes live.** A READ tool chosen after a routed decide call has a routed tier, so a `CONDITIONAL` Grant can now resolve `ALLOW`/`DENY` from evidence (V1 decision pack §1, item 2). That is intended behaviour, and it gets its first real test.
- **Performance samples.** A loop Run counts as one sample under its resulting tier (existing rule). Mixed-tier loops blur that row. It is recorded, not changed.

## 4. Agent Builder design

### 4.1 Mapping to existing concepts (no second permission system)

| Builder field | Stored as | Notes |
|---|---|---|
| name, role, objective, instructions | `agent_definitions` columns | Existing |
| capabilities + per-capability autonomy | `capability_grants` rows (`permissions`, `autonomy_state`, `max_trust_level_required`) | Existing validation, ceiling and 409 rules. **"Autonomy level" in the UI is the Grant's `autonomy_state`**, shown per capability |
| model / tier preference | Proposed `agent_definitions.execution_profile.preferredTier` (D3) | Maps to `taskDifficulty` in plans (CHEAP→simple, MID→standard, STRONG→complex). Risk and escalation floors still raise it; performance still only raises. No Router change |
| work mode + default loop limits | `execution_profile.loopDefaults` (D3) | Pre-fills the agent's objective workflow step. The enforced values are the **step parameters**, immutable in the Workflow version |
| memory scope | `memory_policy` (existing, unread) | Shown as an honest absence: "Memory is not built (V3); stored, not enforced". No enforcement is invented |
| escalation policy | `escalation_policy` (existing, unread) plus the loop's gate / `escalateWhen` | Text only until used by a loop step |

### 4.2 Write flow

- **Create:** `POST /agent-definitions` with an optional `grants[]`. Proposed extension: one transaction calling the existing `createAgentDefinition` and `createCapabilityGrant`, so an agent never exists half-granted. Inserts stay in `registryWrites.ts`.
- **New version:** the same route with `previousVersion`. The UI pre-fills from the latest version and copies its Grants for editing. It then offers "Update workflows that name v*n*", which creates new Workflow versions through the existing route, one explicit act per workflow. Old versions, their Runs, Grants and Workflows stay untouched and attributable (`runs.agent_definition_id/version`).
- **Revoke:** the existing `POST /capability-grants/:id/revoke`, with confirmation. It closes pending Approvals as today.
- **Autonomous agent:** when an agent is created with work mode "objective", the UI also creates its **objective workflow**. That is a one-step `agent_objective` Workflow Definition named `<agent> · objective`, bound to that version. "Give an objective" then calls `POST /goals` with it. The operator can see this in the Workflows list, so nothing is hidden.

### 4.3 Read side

Current status, recent activity, performance, usage and grants already come from `GET /agents/:id`. Versions come from `GET /registry` grouped by name. The agent's objective workflows come from the same source.

## 5. Workflow Builder design

### 5.1 Model

It stays the **linear graph** and the existing interpreter. There are two additive, optional step keys, which are already tolerated by `isStep`:

- `stepId` (a stable string): later graph edges and branch conditions reference it.
- `label`.

A richer `{kind:"graph", nodes, edges}` form can be added later, keyed by `stepId`, without migrating stored graphs.

### 5.2 Generic step kinds

Registered in `src/capabilities/`, seeded as ordinary Task Definitions through the Registry:

| Kind | Plan | Output |
|---|---|---|
| `agent_task` | Resolve inputs, then LLM (`step.instruction`, agent instructions, input artifacts), then deterministic persist | `deliverable` Artifact |
| `agent_objective` | §3 | `deliverable` + `agent_ledger` |
| `operator_checkpoint` | Tool Invocation of the checkpoint capability, snapshot `{question, artifactIds, artifactHashes}` | Approval, then `checkpoint_passed` result |
| `research_report`, `publish_report` | Unchanged | Unchanged |

### 5.3 Inputs and outputs

A new step parameter `inputs: [{ fromStepId, artifactType }]` is resolved deterministically by one shared helper, `resolveStepInputArtifacts`. The rule is the latest artifact of that type from that step's completed Run. It is validated at write time: the referenced step must be earlier. The result is passed to the Compiler as `candidateArtifactIds`.

This is the "step output → input binding" left open in ROADMAP §6. It binds by reference, as §18.2 intends, and adds no variables. To validate parameters at write time, `registerTaskPlanBuilder` gains an optional `validateStepParameters`. `createWorkflowDefinition` calls it by kind, so core still names no capability.

"Configure outputs" in V1.1 means the deliverable title and format hints in step parameters.

### 5.4 Approval gates

Two forms, both existing semantics:

- **Gate by Grant:** any tool step whose Grant is `ALWAYS_APPROVE` pauses for Approval (Publisher today). The composer shows this per step ("this step will ask you first").
- **Explicit gate step:** `operator_checkpoint`. It needs a capability (`review.checkpoint`, a no-op internal adapter, static risk `high`) and an agent holding it at `ALWAYS_APPROVE`. The Approval pins the hashes of the artifacts being approved, so a later change invalidates it. See decision D8.

### 5.5 Composer UX

- A structured step list: add, remove, reorder (move up/down), per-step agent picker (latest versions, with Grants shown), task picker, instruction, inputs picker (earlier steps only) and loop limits for objective steps.
- A live validation panel shows the same checks the Registry runs, server-side via a proposed `POST /workflow-definitions?dryRun=1` (SHOULD).
- **Save** creates a version. **Run** calls `POST /goals` with `async: true`.

### 5.6 Branching and parallel

The spec gates these to V3 on a real workflow's need, and roadmap §10 says not to design a schema ahead of it. Recommended:

- **SHOULD (if D7 approves):** forward-only conditional *skip*. A step has `when: { stepId, field, equals }`, evaluated by plain code on an earlier step's structured deliverable field (for example `evidenceSufficient`). It emits `task_instance_skipped` (named in §8.2, reserved) and never loops back.
- **DEFER:** back-edges and loops (served today by an `agent_objective` step), parallel and merge (the slot model is one Task Instance per step), and a visual graph editor.

## 6. Deliverable rendering design

**Artifact = machine truth, unchanged.** Rows stay immutable, hashes stay over the stored bytes, and provenance is untouched.

**`DeliverableV1`** is the content of a `deliverable`-type Artifact, produced as structured output and persisted deterministically:

```
{ format: "deliverable/v1", title, executiveSummary (markdown),
  body (markdown: headings, lists, tables, emphasis),
  findings?: string[], recommendations?: string[],
  sources?: [{ label, ref?, artifactId? }],     // artifactId sources are checked to exist in this Run/inputs
  completion?: { status: "complete" | "incomplete" | "escalated", reason } }
```

Legacy `report` artifacts (`{report}`) render through the same view: body is the markdown, and the title comes from the Goal.

**Web.** `web/components/deliverable/DeliverableView.tsx` has three tabs:

- **Document** (default): title, summary, body, findings, recommendations, sources, and a completion badge using the runtime's word.
- **Provenance**: the existing produced-by chain, plus id, type, version, size, sha256, stored inline or at a path, created time and referenced-by. **"Verify integrity"** re-reads `GET /artifacts/:id?full=1`, where the server recomputes the hash, and shows match or mismatch with the time checked. A mismatch shows the document under the existing "Untrusted" treatment.
- **Raw**: the existing `<pre>`.

Deliverable types load full content, which is bounded.

**Markdown renderer.** `react-markdown` + `remark-gfm` (tables). It produces React elements only: no `rehype-raw`, no raw HTML, images off, links as text or `rel="noopener noreferrer"`. This keeps the "model output never renders as HTML" rule. It is a new dependency and needs a D3 design-decision record. See decision D5. Hand-writing a GFM table and list parser is more code and more XSS surface.

**Also:**

- SHOULD: the Approvals preview uses the Document view.
- SHOULD: a trivial "Copy markdown" button.
- DEFER: file export or PDF.

## 7. Keeper design

The Keeper is **read, explain, propose**. It has three paths, cheapest first. Being visible starts nothing: no polling, no Run.

### 7.1 Explain (deterministic, no LLM, no Run)

`GET /keeper/explain?subject=workflow_run:<id>|approval:<id>|agent:<id>|goal:<id>|artifact:<id>|system`

It returns a structured explanation composed by plain code from the existing read-model queries, factored into a shared read module used by both the routes and the Keeper. Examples:

- A Workflow Run is "waiting" because Invocation *n* of step *s* awaits Approval *a* (capability, permission, Policy basis, TTL). Alternatives: it is `paused`; a stop engaged at scope X; step failed with reason and `errorCode`; budget denied on counter Y (amounts per unit).
- An agent's Grants, what each allows, and at what autonomy.
- What a budget counter means.

The page passes its current subject, so "Why is this stuck?" needs no model.

### 7.2 Guide (deterministic retrieval, no LLM)

`GET /keeper/guide?q=` runs term matching (reusing `localCorpus` search code, not the tool adapter) over **curated concept cards** in `docs/keeper/*.md`: run vs invocation, create an agent, create a workflow, budgets, approvals, stops, what the system can and cannot do. It returns the best cards with their paths. Cards are written as part of V1.1 and checked against the spec in review.

### 7.3 Reason (governed LLM, explicit)

The operator presses **"Ask the Keeper to think (uses subscription quota)"**. `POST /keeper/questions {question, subject?}` then creates a Goal in a seeded **Keeper** Project, running a one-step `keeper_answer` workflow bound to a seeded ordinary **Keeper** Agent Definition. Its plan:

1. **Tool `system.inspect` (READ):** `prepare` builds the bounded subject snapshot with the §7.1 code (caps per list, summaries not payloads).
2. **Tool `docs.retrieve` (READ):** local corpus over `docs/keeper` and `docs/architecture`, top *k*.
3. **LLM `answer`:** returns `{answer (markdown), citations[], proposals[]}`.
4. **Deterministic:** persist a `keeper_answer` Artifact.

Every governance step applies: Grants (READ only), Policy, Day and Task Instance budget, stops and events. The Keeper **holds no capability with an effect**, and `system.inspect` is structurally read-only (a test asserts its module performs no insert or update).

**Proposals** are data, for example "create Analyst with Grants …". The UI renders them as "Open in Agent Builder" with the form pre-filled. Only the operator's submit writes, through the normal Registry route.

**Why a Goal rather than a new standalone-task driver.** The existing driver is keyed by Workflow Run. A Keeper Project reuses the whole chain with zero runtime change. The cost is Keeper Goals listed under their own Project, which is honest. The alternative, a standalone Task Instance driver, is a runtime change for no capability gain.

### 7.4 NPC

- **Placement:** the unused `entrance` room (`web/lib/keep.ts:19`), a Rogue sprite strip (generated with the existing `make-outlined-strips.ps1`), idle. It is never assigned by `characterFor`, which is reserved for agents.
- **Plaque:** "Keeper" opens a side panel with subject-aware explain, a guide search box, and the explicit reason button with a quota note.
- **While a question runs:** it shows the real Run's status from events. There is no invented thinking animation state.
- **Light:** no state hue.

## 10. Runtime changes

1. **R1:** `SKIP` resolution for deferred positions (`executeRun`, `types.ts`). Tests pin that completed positions are still never re-resolved and that a SKIP proposes nothing.
2. **R2:** background drive for `async` Goal starts. It reuses `advanceWorkflowRunUntilBlocked`, logs failures, and relies on the existing startup re-drive for crashes.
3. **R3:** `validateStepParameters` hook on plan registration.
4. **R4:** event type `agent_loop_iteration_recorded` (additive, §8.2 extension).
5. 6. Retry policy: `agent_objective` not retried (D6).

## 14. Risks

1. **Loop cost versus current ceilings.** The Task Instance ceiling is 50,000 subscription tokens, shared across attempts. A 12-iteration loop at about 2–4k tokens per call (decide + act) will likely hit it. This makes D4 blocking for DoD J–O.
2. **Retrieval is a stub.** Seeded `research.retrieve` returns fixed fake results. An "opportunities" deliverable would rest on model knowledge, with no verifiable sources. It proves governance, not usefulness (DoD O). Mitigation (D10): seed a `local_corpus` binding version over an operator-curated folder. Sources that aren't artifact-backed are labelled "unsourced". A real search provider stays a separate decision (provider, credentials, spend).
3. **SKIP relaxes a documented invariant.** Mitigation: the upper bound stays structural; determinism tests; adversarial review of R1 before merge.
4. **Model-reachable tool inputs.** Mitigation: per-capability loop-action schemas; risk inputs computed by code; Policy authoritative; tests.
5. **Async start and concurrency.** A background drive runs alongside approval, TTL and revoke re-drives. The existing `FOR UPDATE` on `workflow_runs` and the single-executor lock serialize them. It needs a real-connection concurrency test.
6. **Performance-projection blur.** Loop Runs mix tiers, and Conditional Autonomy becomes reachable. Both are recorded, and no rule changes.
7. **Grant-before-use UX friction.** Editing an in-use agent needs a new version plus a new Workflow version. The UI must make this one guided flow, or operators will find it confusing.
8. **Scope.** This is 4 pillars plus the loop. The MUST list (§17) is already large; the order in §18 ships value early (deliverables first) and keeps each commit reversible.
9. **Next.js 16 specifics.** `web/AGENTS.md` requires reading the bundled docs before writing Next code.
10. **Art assets belong to another workstream.** The Keeper's Rogue strip would be generated into `assets/gamification/adapted/`, which is the design workstream's area ("never stage", CLI1 handoff). That workstream produces the strip, or the operator explicitly OKs M5 doing it.
11. **Live structured-output shapes.** Only `{report: string}` has been proven live with `--json-schema`. DecisionV1 and DeliverableV1 have nested and optional fields. M6 includes one authorized live check of each, following the precedent in decision pack §4.

## 15. Architecture-change records (need explicit approval)

**R1: early end of a bounded plan (`SKIP`).**
1. *Problem:* an autonomous agent must be able to stop when its objective is met.
2. *Evidence:* `executor.ts:1545-1661` completes a Run only at the end of a fixed array, and `types.ts:151-160` forbids a deferred position from removing itself.
3. *Current limitation:* a loop would have to run all `maxIterations` or waste Invocations on no-ops.
4. *Proposed change:* a deferred position may resolve to `SKIP`; the length upper bound is still fixed at build time; the Executor proposes nothing and continues.
5. *Alternatives:* a growing plan (removes the bound); no-op deterministic Invocations (noise and false activity); one Task Instance per iteration (the Workflow would delegate topology to a model, which §3d forbids).
6. *Migration impact:* none; existing plans never SKIP.

**R2: asynchronous Goal start.**
1. *Problem:* loops and multi-step workflows run for minutes; the UI must observe rather than wait.
2. *Evidence:* `routes/goals.ts:150` drives inside the request.
3. *Current limitation:* long requests; the UI form warns about it; a retry double-starts a Goal.
4. *Proposed change:* opt-in `async: true`, 202 after commit, in-process drive.
5. *Alternatives:* a job table or queue (new infrastructure, not needed); client long-poll (still request-bound).
6. *Migration impact:* none; the default is unchanged.

**R3: per-kind step parameter validation at Registry write.** Additive hook, kind-agnostic, no migration. Alternative: validate only at run time (today), which lets a composer save broken workflows.

**R4: new event type `agent_loop_iteration_recorded`.** Additive to §8.2, same transaction as the ledger artifact. Alternative: derive the loop view from artifacts only (works, but gives the SSE feed no iteration signal).

**Spec amendments to record after approval** (the spec file carries another workstream's uncommitted hunks, so this is recorded as notes in a closure doc, not edits): §3d/§11 SKIP note; §8.2 event; §12 `execution_profile` (if D3); §15.1 screens 2, 3, 6 and 8 built.
