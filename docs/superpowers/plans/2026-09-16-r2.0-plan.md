**Brief:** the operator's R2.0 brief, 2026-09-16. **Predecessor:** `docs/development/V1_1_CLOSURE.md`.

## 1. What this milestone is

V1.1 proved the runtime can *govern* autonomous work. R2.0 has to prove the work is *useful*: real external evidence, affordable token economics, and agents that persist as identities in the keep. Everything below traces to one of two live demonstrations, or it is deferred:

- **Dogfood A — useful governed work.** One mission uses a genuine external capability, records provenance for every piece of external evidence, distinguishes it from model knowledge, and finishes on the agent's own decision rather than on a limit.
- **Dogfood B — a member of the workplace.** An agent is recruited with a chosen appearance, does real work, earns progression from that work, shows it on its profile, and returns to ambient life in the hub without generating a single fake runtime fact.

If either is not demonstrated, the closing report says so.

## 6. Stage 1 — where the tokens actually went

Measured from the V1.1 dogfood's own recorded events (run `d84737a8`, 42,076 subscription tokens, six model calls), not estimated:

| Term | Share | Detail |
|---|---|---|
| Model **output** | **57%** (24,053) | Two thinking acts alone produced 6,527 and 9,042 output tokens. The act directive asks for "the full result as Markdown" with no length bound, and no output cap is passed to the CLI. |
| Compiled **context** | ~30% | Reported primary input is 2–4 tokens per call: the prompt lands in cache-creation tokens, which are not counted. It is then re-paid almost exactly once by the secondary Haiku call. |
| Fixed per-call overhead | ~13% | ≈ 890 tokens per call, whatever the call does. |

So the working cost model is **counted ≈ context + ~890 + output**, and the "6k per call" figure in the V1.1 record is a run average hiding a 2,000–12,674 spread. Two concrete wastes in that one run: 4,982 tokens on the decide whose invented action was refused (already fixed in `26f29db`), and 7,924 tokens stranded because the headroom check reserves 21,600 for an iteration that actually costs ~13,000.

**Planned reductions, in order, none of which touches a ceiling or a governance check:**
1. **Bound intermediate output.** Cap what a thinking act writes (it only feeds the ledger and the final write) more tightly than the deliverable itself. Largest single lever, est. 17–26% of a run. **Verified live on 2026-09-16** (one minimal call, ~1k tokens): the runtime has no output-cap flag, but it *does* honour a schema `maxLength` — asked for 300 words under a 40-character cap, it returned 37 characters. So this needs no new mechanism and no decision: it is a bound in the output schema the loop already sends.
2. **Merge decide and act for thinking actions only** — one call instead of two, saving its overhead, its re-paid context and its decision output (est. 20–30%). Tool and gate actions must stay split, because the Approval pins the immutable decision artifact.
3. **Honour a deterministic finish** — `done: true` without an explicit finish action currently does not stop the loop, wasting a whole iteration when it happens.
4. **Trim the decision's own output** — `assessment` is stored and never read by any code.
5. **Compact the ledger and refer to prior results by id.** This also removes a latent cliff: at around iteration 8–9 the ledger crosses the decide budget and is silently excluded from context entirely.
6. **Re-size the loop's reservations** — but only after output is bounded, because today's estimates already *under*-shoot actual acts.

**Done in this phase (2026-09-16):** reductions 1, 3 and 4 are built — every model-written field now carries a length bound and every list a size bound (`OUTPUT_CAPS`, `DELIVERABLE_CAPS`), and a decision that says the objective is met now ends the loop instead of buying another iteration. That second one exposed a real defect: the loop stopped for the right reason and then *reported* the wrong one, because the terminal reason is re-derived at conclude rather than recorded when the stop happens. Both the stop and the conclusion now use the same rule. Reductions 2 (merge decide and act) is refused by D12; 5 (ledger compaction) and 6 (re-sized reservations) remain.

**Measurement harness:** a read-only query over existing events (`invocation_completed` usage, `context_compiled` sizes and exclusions, `agent_loop_iteration_recorded` outcomes) plus a mocked regression asserting call counts and shapes, so no future refactor can quietly add a round-trip. Two gaps to close first: per-layer attribution (instructions and the invocation instruction are never itemised) and the secondary model's usage (recoverable by arithmetic today, unrecoverable at CHEAP).

**Honest caveat:** all of this optimises the *counted* metric. Whether cache-creation tokens draw on real Max entitlement is a documented unknown; if they do, context becomes far more expensive than the counted numbers suggest and reduction 5 rises sharply in value.

## 7. Architecture positions (no second anything)

1. **No new permission system.** Research and every external capability run through Capability → Grant → Policy → Budget → Approval, as data plus a registered adapter.
2. **Progression never touches authority.** It gets no eligibility gate, is not imported by governance, router or execution, and — importantly — never enters a compiled context, so an agent cannot optimise for its own XP.
3. **Lineage is the agent's name**, already structural via the unique `(name, version)` index. The spec's per-version XP key contradicts persistence across versions and needs correcting.
4. **Pixel art: the ambition needs new art, and two decisions first.** The inventory is blunt. The characters that match the keep's scale are Knight, Rogue and Wizzard (plus a nude base body): the Rogue is already the Keeper, and the Wizzard's purple collides with three identity tints, so **about two identities exist today and roughly seven or eight are reachable by recolouring**. Every sprite is flat and fully baked — there is no hair, clothing or equipment layer in any pack — so the Builder can offer **presets plus a palette, not mix-and-match**, unless layered art is drawn. There is **no walk animation, one facing, and no sit or rest pose** for any of these characters, and no walkable-area or seat data of any kind. So an idle agent that walks to a rest room needs generated art: walk strips with at least two facings, sit/rest poses, a rest room in a recomposed keep, and a waypoint map. All of it must follow the existing pipeline (read-only over the source packs, scripts and output under `assets/gamification/adapted/`, whole-number scaling, baked outline, identity tints only — never state colours).
5. **Ambient life is presentation.** No backend, no game engine, no network traffic from movement, no ambient state that the runtime does not actually produce.
6. **SSRF is the real work in `research.open`**: refuse loopback, private, link-local and cloud-metadata addresses after DNS resolution and on every redirect hop; cap bytes, redirects and time.

## 10. Agent visual identity and recruitment — implementation plan (2026-09-16)

**What exists.** Identity across versions is already the agent's `name` (unique with `version`). Looks are not: `web/lib/keep.ts#characterFor` and `preferredSlot` key on the *definition id*, so Strategist v2 already renders as a different character from v1 on every screen that draws one (Overview map and board, Agents and Registry close-ups). Two characters exist (Knight, Wizzard, with idle/run/death strips); the Rogue is the Keeper. All Pixel Crawler sprites are flat, so mix-and-match needs new layered art. There is nowhere to store an appearance.

**Model — three things, kept apart.**
1. *Persistent identity*: the agent `name`, as today. No new identity table: the unique `(name, version)` index already makes it structural.
2. *Versioned definition*: `agent_definitions`, unchanged. No appearance column: an edit to a definition must not touch the look, and a new look must not mint a version.
3. *Appearance*: new table `agent_appearances(agent_name PK, appearance jsonb, created_at, updated_at)` (migration 0021). The jsonb holds only **catalogue keys** (`skin`, `hair`, `hairColor`, `top`, `topColor`, `bottom`, `bottomColor`, `accessory`, `mark`), never image data. One catalogue file is the source of truth for the generator, the API's validation and the builder's options.

**Rules.** A write names a key that is not in the catalogue → 400. A stored key the catalogue no longer has → that part falls back to its default on read, never an error. An agent with no stored appearance keeps a legacy character (Knight/Wizzard), now keyed on its **name**. No event is emitted: an appearance is presentation, not a runtime fact, and nothing in Policy, budget, routing, context or performance reads it (structural test).

**Art.** `assets/gamification/adapted/make-agent-kit.ps1` layers clothing, hair, accessories and a role mark over the pack's `Body_A` base, frame by frame (idle 4, run 6), anchored to each frame's own head and body bounds, cropped 34×34 and scaled 2× nearest-neighbour. Outputs go to `adapted/agent-kit-2x/`; originals untouched. Colours come from the identity tints plus neutrals, never the state hues. No death strip: a failed custom character holds its idle frame and the existing failure overlays carry the state.

**Recruitment.** The Agent Builder gains a **Character station** (live 4× preview + choices) saved with the recruit. Versioning shows the character read-only. The agent board gains **Change appearance**, which saves only the appearance.

**Rendering.** One layered sprite component, used wherever `AgentSprite` draws an agent; runtime state still chooses the pose. Keeper untouched.

**Out of scope here:** progression, living hub, Keeper, animation beyond idle/run, a general asset pipeline.

**As built (2026-09-16), deviations from the plan above.** The write is `POST /agent-appearances/:name` (not PUT), so the API's CORS surface stays GET/POST. There is no separate `CharacterSprite`: `AgentSprite` takes an `AgentLook` and draws either the kit (layers as one element's stacked backgrounds) or the default strip. Workshop slots are also keyed on the name. Migration 0021's journal `when` was hand-set after 0020's, because drizzle skips an older-dated migration.

## 11. Agent progression — implementation plan (2026-09-16)

**What exists.** Persistent identity = `agent_definitions.name` (versions immutable, the name cannot change across versions). Performance is `agent_performance`, rebuilt from Events, keyed per *version* and read by the Router through the eligibility gate. Its sample rule (Stage 5 corrected: loop `complete` = success, iteration/time limit = failure, budget-headroom / budget / policy / stop / halted = excluded) lives inside that projector's SQL. Events are immutable with a unique `idempotency_key`. `context_compiled` records every included artifact's id **and hash**; a loop's terminal event records `evidence_sufficient` and its code-verified evidence (including `capability: "handoff"` with the handed run). Goals record `goal_completed`, workflow runs `workflow_run_completed`. Approvals are `approval_granted` by `human:operator`. No quality judgement, endorsement, XP, specialisation or achievement exists. No governed "difficulty/high-value" criterion exists (the Router's tier follows the operator's preference and risk, not value).

**Model.**
- *Shared rule, not a second performance system.* The run-sample CTE moves verbatim to `src/projections/runSamples.ts`; `agent_performance` and progression both import it, so they can never disagree on what counts.
- *Progression projection* `src/projections/agentProgression.ts`, rebuilt from Events in one transaction on the same in-process loop (no watermark, idempotent by construction), keyed on the agent **name**. Tables (migration 0022): `agent_xp_awards` (one row per award, unique `(agent_name, award_key)`, rule, xp, the run/workflow run/goal/artifact it rests on, evidence json, earned_at); `agent_achievements` (PK name+achievement, earned_at, evidence); `agent_domain_work` (name, domain, run — the specialisation evidence); `agent_endorsements` (one per completed `peer.endorse` invocation, re-verified, `counted` + `excluded_reason`).
- *Levels* are a pure function of summed XP: threshold(L) = 250 × (L(L+1)/2 − 1) → 0, 500, 1,250, 2,250, 3,500, 5,000, 6,750, 8,750 … (each step 250 larger). One constant, one function.
- *Reputation is not a score.* It is a read model of independent signals with their counts: operator verdicts by grade, and distinct cross-lineage endorsers (endorsements on a cycle excluded). No formula until there is evidence to fit one.
- *Specialisation* = the domain holding ≥ 3 of the agent's successful runs and at least half of them, from a fixed capability→domain map (`research.*` → research; a successful run that finished on a verified handoff → analysis; `publish.report` → publishing). Never from the name, never model-written.

**XP rules (constants in one file; D2 values).** Only runs that are performance *success samples* earn work XP, attributed to the run's agent name.
- task +100: per Task Instance with a success sample.
- research task +100: that run also completed ≥ 1 `research.*` invocation.
- capability use +50: per (success run, distinct capability) completed; not `review.checkpoint` (an approval) nor `peer.endorse` (endorsements are zero XP).
- workflow +250 / mission +500: `workflow_run_completed` / `goal_completed` ("mission" is the Goal, as the agents read model already names it), to each agent with a success sample inside it.
- validated artifact +150: the `deliverable` of a run whose loop concluded `evidence_sufficient` (code-verified evidence, not the model's say-so).
- quality verdict 0/50/150/300: the **latest** operator verdict on an artifact, to the agent whose run produced it.
- difficulty bonus: **not built** — no governed criterion exists; building one would be inventing it. Open decision.
Nothing else earns XP: not approvals, tokens, endorsements, appearance, versions, names, ambient life.

**Quality verdicts.** `POST /quality-verdicts {artifactId, verdict, rationale?}` → one `quality_verdict_recorded` event (actor `human:operator`, the target artifact + hash + producing run in the payload, the previous verdict). Operator route only; a structural test keeps the event type out of every other module.

**Peer endorsements.** A governed capability `peer.endorse` (WRITE, internal binding, loop action `{artifactId, reason}`). Before the Tool Invocation is built, code — not the model — proves the endorsing run's `context_compiled` included that artifact id with its current hash, that the artifact is a `deliverable` produced by a **different agent name**, and that this agent has not already endorsed it; otherwise the action is refused like a missing Grant. The prepared snapshot carries the proven hash and the endorsing run. The projection re-verifies from Events and excludes anything unproven or on a name cycle. Zero XP.

**Achievements (5, deterministic, idempotent):** first successful task; first verified research result (evidence_sufficient with a verified `research.*` item); multi-agent handoff (finished `evidence_sufficient` on a handoff from another agent name); first validated artifact; seasoned in a domain (5 successful runs in it).

**Firewall.** Structural invariant: progression tables, the projector and the verdict event are referenced only by the schema, the projector, the startup loop, the progression routes and (for `peer.endorse`) its own capability module. Governance, router, execution and context never import them, so progression cannot reach authority or a compiled context.

**UI.** Agent board (Agents screen) gains a *Progress* parchment beside the character: level with a segmented XP bar and "N XP to level L+1", plain-language performance across all versions, specialisation or "none yet", achievement plaques, reputation signals or "not enough evidence yet", and a collapsible "How this XP was earned" ledger linking each award to its run/artifact. The artifact Document view gains an operator *Quality verdict* control with its history.

**Not built:** difficulty bonus, reputation formula, progression-based anything in governance, live missions to demonstrate it, living hub, Keeper.

**As built (2026-09-16).** Architecture doc: `docs/architecture/AGENT_PROGRESSION.md`. Deviations and additions: `peer.endorse` acts under **CREATE**; the loop gained one generic hook, `LoopAction.prove`, called with the Run before a Tool Invocation is built (refusal = refused like a missing Grant). Capability-specific meaning (domains, which uses earn no XP, fixture evidence is not research) lives in `src/capabilities/progressionFacts.ts`, so the projector names no capability. ## 12. Stage 6 — Keeper explanations: implementation plan (2026-09-16)

**What exists (V1.1).** `src/keeper/explain.ts`: deterministic, model-free explanations for seven subjects (system, workflow run, goal, approval, agent grants, artifact hash, run) as `{headline, facts, reasons, next}`; `GET /keeper/explain`. `src/keeper/guide.ts`: deterministic guide cards. **Think** (`POST /keeper/questions`): an ordinary governed Goal run by the ordinary Keeper Agent Definition, which holds only READ Grants (`system.inspect` = the explanation above, `docs.retrieve` = guide cards), one CHEAP write call, a `keeper_answer` artifact; a proposal only pre-fills a builder. **Design — no new infrastructure.**
1. **Intents** (`src/keeper/intents.ts`): 16 explicit intents, each declaring the subject kinds it accepts and its authoritative source. A deterministic classifier (keywords + an exact agent-name match to resolve "Field Researcher") maps a question to an intent; the UI can also pass the intent directly. An unmatched question gets a bounded "here is what I can explain about this subject" answer.
2. **Explainers** (`src/keeper/explainIntent.ts`): one deterministic query per intent over exactly the rows it needs, returning the contract:
   `{ intent, subject, headline, facts[], derived[], unknown[], links[], sources[], size }` where each fact/derived line carries `source` (the authority, e.g. `agent_xp_awards`, `events.policy_evaluated`) and optional record links. Caps per section and per line; `size` = characters and estimated tokens (the Context Compiler's estimator). Model-written content (decisions, deliverable text) is never read as a fact.
3. **Authority table** (in code, tested): XP → `agent_xp_awards`; level → `levelFor(xp)`; performance → `agent_performance`; quality → `quality_verdict_recorded` events; achievements → `agent_achievements`; specialisation → `agent_domain_work`; endorsements → `agent_endorsements`; run outcome → run/loop terminal events; evidence → loop terminal `evidence.verified` + recomputed artifact hash; handoff → verified `handoff` evidence + both runs; policy → `policy_evaluated`/`approval_*` events; budget → `budget_consumed` events + counters; model/tier → Router `invocation_started`; stop → loop terminal / `run_halted` / `invocation_failed`; runtime state → unfinished runs + stops; ambient → the documented presentation mapping (and "no ambient life exists yet").
4. **Read-only by construction**: `POST /keeper/explanations` runs every explainer inside `SET TRANSACTION READ ONLY`, so a write is refused by Postgres, not by convention. No binding config, env or credential is ever read.
5. **LLM only to phrase**: Think keeps its governed path; `system.inspect` now returns the intent bundle for the question (intent recorded on the Goal next to the subject), and the directive tells the Keeper to restate FACT/DERIVED, keep UNKNOWN unknown, and never add a number. A deterministic post-check in the persist step lists any number in the answer that is not in the bundle (`unsupportedNumbers`), shown in the UI. Model output stays untrusted.
6. **Firewalls**: the progression and `agent_performance` invariants gain the Keeper explainer as a named read-only reader; nothing in governance/router/execution/context imports it.
7. **Identity**: `GET /keeper/identity` returns the Keeper's persistent definition and appearance; the dock, panel and entrance draw it through the existing appearance system, falling back to the Rogue (D22) when none is set. No new character system; no new Grants.
8. **UI**: the Keeper panel gains an **Explain** section — question box plus intent chips for the page's subject — rendering FACT (with source tag and links), DERIVED and UNKNOWN; the agent Progress card gets "Ask the Keeper why" shortcuts. Think stays, now labelled as putting the same facts into words.
9. **Live proof**: deterministic layer proven on existing Stage 4/5/progression history; at most one bounded Think call if needed, tokens recorded.

**Not built:** conversational memory, shared memory, open-ended agent, retrieval/vector store, new capabilities or Grants for the Keeper, living hub.

**As built (2026-09-16).** Architecture doc: `docs/architecture/KEEPER.md`. The route is `GET /keeper/explanations` (reads are GET here), run with `accessMode: "read only"`. An independent review found and I fixed: agent-name matching built a regex from the name and had a broken word boundary (a name like `C++ Bot` would have made every explanation fail; "researchers" matched "Researcher") — replaced by a plain whole-word scan; the Keeper's own name is ignored beside another agent; the number tripwire now compares only with the records' text, not ids, hashes, sizes or the question; Think keeps the general explanation when a matched intent found no records; truncated runs, policy records and routes keep the newest and say what was left out; calculations moved from FACT to DERIVED; stops at run, workflow-run or goal scope now count in the ambient answer. ## 16. Manager / Orchestrator (2026-09-16, as built)

## 17. Manager reliability hardening (2026-09-17, as built)

- **Driving.** `advanceWorkflowRunUntilBlocked` now continues any Workflow Run a step starts on the same Goal during the drive (≤3, only runs that did not exist before). Every driver gets it: async start, approval decision, expiry sweep, grant-revocation re-drive, manual advance and startup re-drive. Before, delegated or follow-up runs started during an approval or startup re-drive were never driven, and the stuck run 409'd every new mission.
- **Completion.** A worker whose own loop recorded `incomplete` (max_iterations, active_time_limit, budget_headroom) can never be completed by the model's "sufficient".
- **Stale plans.** The start step re-validates the record's tasks against the database at the last boundary (grants, stops, busy agents — now including work assigned but not started — reserved step ids, mission limits, 30-minute window), binds the agent versions that exist then, and writes the Workflow Definition, run and event inside one savepoint. `manager.delegate.prepare` keeps the provenance check (code-written record, hash intact, from a `manager_plan`/`manager_review` step, `delegate: true`).
- **Reasons.** Deterministic codes (`src/capabilities/manager/capability.ts` `MISSION_REASONS`) on plan/review records and in `GET /manager/missions/:goalId` (`reason`, `reasons`), derived from run outcomes, `invocation_failed`, Policy decisions and code-written records; model text only as `detail`. `stopped` now comes from the failing run's own outcome, not any `run_halted` on the goal.
- **Recovery rule.** Follow-up only when every finding is recoverable: `evidence_invalid`, `deliverable_invalid`, `worker_timed_out` (loop time limit). Never for verification failure, budget, stops, approvals, missing capabilities or a failed worker run (the review cannot run after a failed step without changing step-input semantics — out of scope).
- **Read model.** One read-only repeatable-read snapshot (fixes a transient `finished_without_report`); JSON parsing guarded; mission records read only from the step kinds that write them; a `trace` of Manager decisions and governance facts from the existing events.
- **Context.** Roster: version, "available", boilerplate specialities and the note dropped — 632 → 407 estimated tokens on the dev workforce. Review verification record no longer carries artifact ids, hashes or run ids (joined back by code for the report).
- **Found, not changed:** `secondaryUsage` from the router is dropped at emit (`modelRouter.ts:793` → `events/emit.ts`), so the CLI's Haiku classifier tokens on Sonnet worker calls (8,497 of the live mission's 29,443) are charged but not attributable per call; `tokens_out` includes CLI thinking not recorded separately; deliverables handed to downstream steps repeat summary/findings (~870 tokens in the live review) through shared `agent_objective`/compiler paths.

## 21. Organisational autonomy: truthful rooms and governed Manager recovery (2026-09-18, as built)

- **Rooms on the map (Stage 0.5).** A seeded meeting room named one hard-coded area ("Council hall", "Vault"…), so any world template without that area left the room — and every meeting in it — off the map with nothing saying so. `DEFAULT_ROOMS` now carries an ordered list of candidate areas; `ensureDefaultRooms(tx, actor, areaNames)` creates each room on the first candidate the current world actually has, and **repairs** a seeded room whose area this world no longer has. `POST /world` (create and template switch) re-places the rooms, meetings kept. `GET /workplace/settings` returns `rooms[].onTheMap`, `offTheMap[]` and `areas[]`, so a room with nowhere to stand is named rather than hidden. The workplace module still never reads world tables: the caller passes the names (`activeAreaNames` in `src/world/worldConfig.ts`).
- **Why recovery (Stage 1).** Delegated work that failed ended the mission. Nothing diagnosed it, nothing tried again, and the operator got a reason code and no further action.
- **Classification is code, not a model.** `src/capabilities/manager/failure.ts`: `classifyRunFailure` reads the Run's outcome, its last `invocation_failed`, the Policy decision behind a denial and the step's kind — never model text. `diagnoseWorkflowRun` walks the failed Workflow Definition's steps against `variables.stepTaskInstanceIds` and returns which step failed and why, which steps had already completed, and which were never reached. The mission read model uses the same classifier, so the operator and the recovery say the same words.
- **What a failure allows.** `RECOVERY_BY_REASON` (`capability.ts`) maps each `MissionReason` to the actions a recovery may propose: `provider_unavailable` → retry/reassign/escalate; `worker_timed_out`, `worker_failed` → reassign/modify/escalate; `budget_denied`, `emergency_stopped`, `capability_unavailable`, `approval_rejected` → **escalate only**. The model chooses from the allowed list; it cannot widen it.
- **The step.** Seeded Task Definition "Manager Recovery" (`manager_recover`) and a one-step Workflow Definition of the same name, pinned to the latest Manager. Seven positions: det diagnose → tool inspect workforce → LLM propose → det validate (emits `manager_recovery_decided`) → `manager.delegate` → det start → det persist. `delegateAndStart` is the same pair the plan and review use, so the delegation is re-validated against the database as it is then. The recovered task **keeps the failed task's own tools and intents** — the model may not widen what the work may use — and `reassign` to the agent that just failed is refused.
- **The trigger is bookkeeping, not a decision.** `maybeStartRecovery` (`src/api/routes/manager.ts`) runs under an advisory lock per Goal and refuses unless: the Goal is in the Missions project, nothing is in progress or paused, the mission is inside its 30-minute window and its run allowance, no recovery has run yet, the last failed run was delegated work (never the plan or a recovery), at least one failure allows something other than escalation, and no stop is active. Then it starts the run and emits `manager_recovery_started`. The Manager cannot start it.
- **Run allowance.** `maxWorkflowRuns` stays 3 — the runs a mission may *plan* (plan, delegated work, one follow-up). A recovery may add `maxRecoveryWorkflowRuns: 2` on top (itself and the run it delegates), and `maxRecoveryRounds: 1` bounds it to one round. A review's follow-up can never spend the recovery allowance; the recovery run is driven on its own, so the interpreter's `MAX_FOLLOW_ON_RUNS` is unchanged at 3.
- **Every path, not just the first.** The mission's own driver runs the recovery after its drive. Missions failed elsewhere — an approval decision's re-drive, a restart — are covered by `sweepMissionRecoveries`, a third 60-second loop in `src/api/start.ts`. Generic runtime code still knows nothing about missions.
- **A recovered mission reads as recovered.** A Goal with any failed Workflow Run is derived `failed` and stays so, which would have shown the operator a failed mission holding a completed report. The mission read model now treats that failure as historical once a "Manager Recovery" run completed and the work it delegated finished; the failure stays in `steps`, `reasons` and `recovery`. A recovery that escalated is the last run on the Goal, so the mission still reads failed.
- **Every decision leaves a trace.** A refused recovery previously returned before its event; now the decision is computed first and `manager_recovery_decided` is emitted for refusals too. `GET /manager/missions/:goalId` gains `recovery` (`{ round, failures, action }`) and both events appear in the mission `trace`.
- **No god-mode.** The recovery grants nothing, changes no budget, lifts no stop, approves nothing, marks no failed work done, writes no runtime rows. The structural invariant now forbids the Manager module writing `runs`, `task_instances`, `workflow_runs`, `workflow_definitions`, `invocations` or `goals` directly — it goes through the Interpreter and the Registry.
- **Proof.** 8 recovery tests in `tests/api/managerReliability.test.ts` (20 to 28 in that file), against the real runtime with mocked model calls: the full reassign path (Plan → work failed → Manager Recovery → replacement work reviewed and completed); one round only; reassign to the failed agent refused; an unknown agent refused; no recovery for an emergency stop, a failed plan, or a mission that never failed; and recovery through the sweep after a generic re-drive.
- **Known, not hidden.** Between the delegated run failing and the recovery starting, the mission truthfully reads `failed` for a moment (two separate transactions); the tests wait for the mission to stop moving rather than pretend otherwise. Retry-as-such is only reachable for `provider_unavailable`. `notReached` steps are reported but not re-planned: a recovery delegates one task.

## 22. Multi-agent handoffs: what is real, what is not (2026-09-18, audited and hardened)

Audited before changing anything (file:line evidence in the session record). The honest position:

- **`dependsOn` is data flow, never scheduling.** The Manager's validator (`src/capabilities/manager/mission.ts:243`) only allows it to name an earlier task of the same plan, and `missionGraph` (`:274`) turns it into step `parameters.inputs`. Nothing in `src/workflow/interpreter.ts` reads it. Execution order is the order the Manager listed the tasks in; that order is a valid topological order **by construction**, not because anything schedules it.
- **It is not inert, though.** Through `parameters.inputs` a declared dependency can fail the downstream step closed (`stepInputs.ts`), raises that step's per-decision context budget, seeds its ledger's input labels, unlocks the "handoff" evidence branch, and inherits the upstream evidence basis into the downstream deliverable.
- **The handoff itself is by reference and positional.** `resolveStepInputArtifacts` finds the source step's slot in `variables.stepTaskInstanceIds`, requires exactly one completed Run and exactly one artifact of the declared type, and hands the downstream agent **only the artifact id** as a Context Compiler candidate. The agent never names the artifact; code chooses it. It arrives fenced as untrusted data.
- **Integrity, newly closed.** The resolved `hash` was carried into records but never verified against content anywhere. `resolveStepInputArtifacts` now recomputes the SHA-256 of the stored content and fails the step closed on a mismatch — provenance says it came from the right run, this says it is still what that run wrote. Proven twice by writing around the immutability trigger: at the unit boundary in `tests/api/workflowBuilder.test.ts`, and at mission level in `tests/api/managerReliability.test.ts`, where a dependent worker's step fails closed rather than reasoning on tampered evidence.
- **Who checks integrity, and who judges it.** A worker consuming evidence fails closed on a hash mismatch. The Manager's **review** resolves its inputs with the check off (`verifyIntegrity: false`) on purpose: its `verify` step already compares each artifact to its recorded hash and reports a mismatch as `verification_failed` with the failing step named. Failing it closed there would have replaced a reasoned verdict with an opaque `execution_error` — found by a test that had been passing for the right reason before, and would have started passing for the wrong one.
- **Incomplete work is no longer handed on silently.** An upstream loop that ran out (`max_iterations`, a time or budget limit) still writes a deliverable and completes its Run. The downstream agent's input label now says `RECORDED INCOMPLETE (<reason>)`, so partial work cannot pass as finished work just by being handed over.

**Not built, and not faked — reported as limits:**

1. **No parallelism.** The interpreter is strictly single-active-step per Workflow Run (`interpreter.ts:829-869`), and follow-on Workflow Runs on a Goal are driven serially. Two agents can never work at the same time on one workflow. True parallelism needs a second scheduling engine, which this milestone's "no second runtime" position rules out.
2. **No DAG and no scheduler.** The graph type has no edges at all (`graphTypes.ts:29-54`).
3. **No waiting/blocked state.** Step statuses are `active | awaiting_approval | completed | failed`. "Blocked" in `advanceWorkflowRunUntilBlocked` means the driver has nothing left to do automatically — never "waiting on a dependency". There is no truthful runtime fact for "waiting for another agent", so none is displayed.
4. **No partial-failure semantics.** Any step failure fails the whole Workflow Run (`interpreter.ts:875-885`); nothing is skipped or degraded. The Manager's recovery round (§21) is the answer to a failed step, at the mission level.
5. **No cross-run handoff.** `fromStepId` resolves only within the same Workflow Run, so a Manager follow-up or recovery starts with `dependsOn: []` and cannot be handed the earlier run's deliverable by reference.

## 23. Meetings the Keep actually holds, and deadlines (2026-09-18, as built)

Audited first. The premise "there is no record of what happened in a meeting" was wrong — `notes`, `decisions` and `actions` columns and an operator write path existed. What did not exist: any way for the meeting to *happen*. A meeting was a diary row whose `completed` meant only that the clock had moved past `endsAt`; the participant list was an invite list, never attendance; no agent could record anything; and nothing in the runtime ever made a meeting occur.

- **Convening (Stage 4).** `sweepMeetingsToConvene` (`src/api/routes/meetings.ts`), a fourth 60-second loop in `api/start.ts`, finds meetings whose time has come (begun, not over, not cancelled, never tried) and **holds** them: a Goal in the new "Meetings" Project and a linear Workflow Run that IS the meeting. Migration 0027 adds `convened_goal_id`, `convened_at` and `not_convened_reason` — the first facts in the system that distinguish a meeting that happened from one whose end time has passed.
- **The round table.** One `meeting_contribution` step per participant, in turn, then one `meeting_outcome` step for the Manager. Each agent speaks in its own role with the agenda and everything already said in front of it. **A round table is sequential by nature**, so it fits the linear interpreter exactly and needs no parallelism the runtime does not have (§22). Every word is a real Invocation under that agent's own Grants, Policy, budget and stops, with an Artifact and provenance. Nothing invents a conversation.
- **A contribution is not evidence.** Contributions are written as `meeting_contribution` Artifacts, never `deliverable`. `INPUT_ARTIFACT_TYPES` accepts only `deliverable` and `report` and `carriesRecordedEvidence` requires a `deliverable`, so **by construction** no step can take what someone said in a room as verified evidence, and the recorded basis says so in words. They reach the next speaker as compiled context, fenced like any other untrusted document.
- **A meeting that cannot be held says so.** Every participant must actually be free — `unavailabilityCode` with a new `ignoreMeetingId` (being in *this* meeting is the point, not a clash). If anyone is stopped, working or in another room, `not_convened_reason` records who and why. It is never quietly skipped and no step ever pretends someone attended.
- **Recording the outcome is governed (Stage 4).** New Capability `workplace.record_outcome` (WRITE), its own Grant on Manager v3, separate from `schedule_meeting` so an operator can require approval for what a meeting concluded while leaving the diary autonomous. Four positions: LLM proposes → code validates and caps → the Capability is checked → code writes through `recordMeetingOutcome`, which already refuses a meeting that has not begun. A meeting that settled nothing records its notes and no decisions; a meeting that produced neither records nothing and never reaches the Capability.
- **Decisions become work, the operator decides (Stage 5).** `POST /workplace/meetings/:id/actions` turns a recorded decision into an ordinary governed Manager mission and links the Goal back to the meeting. This now works on decisions the *agents* reached, not only ones the operator typed. **Deliberate authority choice:** the Manager may record what a room decided but may not turn its own conclusion into new work — that would let it create Goals from its own reasoning. The route refuses the same decision twice.
- **Deadlines (Stage 6).** `goals.due_at` (migration 0027), set only by the operator on `POST /manager/missions` and only in the future. The Manager's plan directive gains a code-computed fact — the deadline and the minutes left — and is told explicitly not to estimate durations, promise a completion time, or cut a completion criterion to look faster. `GET /manager/missions/:goalId` returns `dueAt` and an `overdue` **derived from the clock**, like a meeting's status. A mission is never failed for being late: the operator decides what an overdue objective is worth. `maxMissionMinutes` remains a spend cap measured from `createdAt`, not a deadline.
- **Proof.** 9 tests in `tests/api/meetings.test.ts`: a two-person round table convenes, both speak once, contributions are non-deliverable Artifacts, the outcome lands on the meeting stamped with the agent that recorded it, `meeting_closed` names the count; a meeting is held once however often the sweep runs; a stopped participant leaves the meeting not held with the reason and nothing said; a meeting settling nothing records its note; a meeting producing nothing records nothing; a decision becomes a linked mission and cannot be started twice; a bad decision index is refused; a deadline round-trips and `overdue` follows the clock; a bad or past deadline is refused.
- **Found while building.** `codeWrittenRecord` gated governed writes to three Manager step kinds; the outcome step is a fourth. The allow-list is now a named `RECORD_WRITING_KINDS` set beside the check, because adding to it widens what can authorise a write.
- **Not built, and why.** Working hours still gate nothing outside meeting scheduling: an agent is software and a Goal created at 03:00 runs like one at 10:00. Making the runtime refuse work off-hours would be theatre, not truth — the agent daily rhythm is its own stage. No recurring meetings, no external calendars, no attendance beyond "this agent's step ran".

## 24. The agent's day, and a workplace that tells the truth about it (2026-09-18, as built)

Three independent audits first. They found the real problem: **five server-side vocabularies answered "what is this agent doing?" in different words, and the browser derived three more** — and they disagreed. A `break` blocked booking a meeting but not delegation. `outsideWorkingHours` gated meetings and nothing else. "Stopped" was computed five ways with different scope coverage. Almost everything Stage 7 needs already existed and was simply never consulted.

- **Nothing was rebuilt.** The availability engine (`availabilityOf`, statuses with reasons), DST-correct zoned arithmetic (`Intl`, no dependency), per-agent hours, and `break` as a *already-blocking* calendar kind were all there. Stage 7 is mostly wiring, one new switch and one new read model.
- **Where the gate went, and why not the interpreter.** The obvious place — `createAndRunStep` — is wrong. At the only point where no Task Instance exists yet the agent is not bound (`runs.agentDefinitionId` is null at insert; the interpreter "has no channel to learn that binding"), and **no periodic sweep re-drives an idle `in_progress` Workflow Run**, so a deferred step would sit there until a restart. Building that would be the second scheduler this milestone forbids. The gate went instead into `unavailabilityCode` — the existing pre-start boundary, already consulted by the Manager's roster, by plan validation and again at the delegation boundary. Three call sites, one check, no interpreter change.
- **Scheduling and execution are separate switches.** `outsideWorkingHours` answers "may a MEETING be booked then". Reusing it for work would conflate the two and silently change every existing Keep. Migration 0028 adds `workplace_settings.work_outside_hours`, **defaulting to `allow`** — today's behaviour exactly — with an operator control in Settings. Set to `forbid`, the Manager will not give an agent NEW work outside its hours.
- **Starting is not running.** The gate only ever refuses a start. A Run that crosses 17:00 keeps running, is not failed, is not stopped, and still reads as `working`; the same agent may still not be given new work. That is the one semantic the brief insists on, and it is the test that proves it.
- **Convening does not re-ask the diary.** A meeting scheduled outside hours was already settled when it was booked; re-checking at convene time would be double jeopardy and would quietly stop operator-scheduled evening meetings from ever being held. `unavailabilityCode` gained `ignoreSchedule` for exactly that path.
- **One state, computed once (`src/api/agentState.ts`, `GET /agents/state`).** `stopped › awaiting_approval › in_meeting › working › waiting_dependency › on_break › outside_hours › unavailable › available` — authority beats runtime beats diary beats "nothing to do". Every shared read (stops, presence, the diary) happens **once** per call, not per agent, because the world polls it. It writes no row, emits no event, calls no model and awards nothing.
- **`waiting_dependency` is named for what can be proven.** The interpreter is single-active-step, so a later step has no Task Instance until the earlier one finishes. The honest fact is "assigned work whose turn has not come", not "waiting for Alice". **`blocked` was not invented**: this runtime has exactly one blocked state — awaiting approval — and a second word for it would be a lie.
- **Breaks needed no migration.** `break` was already a calendar kind and already blocking; it only ever reached meeting booking. It now gates new work, shows as `on_break` with when it ends, and sends the agent to a rest area. Only `human:operator` can create one — no capability, no adapter, no model path writes hours, settings or calendar entries.
- **The world renders the server's answer.** `desireFor` takes the state as a fact for the three things the browser cannot know (a break, time off the clock, waiting work). New states draw with the poses that **actually exist** — `idle`, `walk`, `work`. There is no sitting or reading art, so a break rests standing and time off the clock draws the agent nowhere at all rather than faking a pose.
- **Three congestion bugs fixed, deterministically.** Overflow workers were each handed the *same* desk object and stood on one pixel — now dealt round the desks of the right kind. `crowdOf` counted only `ambient:` intents, so a room full of waiting agents read as empty — it now counts waiting, queued and break intents too. Waiting and queued agents were all sent to `area[0]` — now spread across every area of the right purpose, weighted by who is already there, preferring the correct purpose before any fallback.
- **Manager integration is one short phrase.** The roster already carried `unavailable` per agent; it now reads e.g. `is outside working hours; free from 2026-09-21 09:00` in the Keep's own wall clock. The model proposes, code checks — the gate refuses at the delegation boundary whatever the model says.
- **Keeper.** Its `ambient` answer no longer claims "no ambient life exists in this build" (it does), and with no unfinished run it now cites the diary — a break, or time off the clock — from the same records its workplace answer uses, so the two never disagree.
- **Progression untouched.** `agent_xp_awards` has exactly one writer, driven from `run_completed` events and completed invocations; no workplace table is read anywhere in it. Being available, on a break, in a meeting, waiting or visible in the office earns nothing, and the new state module writes nothing at all.
- **Tests.** `tests/api/agentRhythm.test.ts` (14): boundary minutes exactly, weekend, configured timezone vs the server's, a DST crossing that does not drift, "next free" without estimating durations, the default that changes nothing, hours and breaks refusing new work, a stop still winning, convening ignoring the diary, a Run crossing the end of the day surviving, and the state endpoint writing nothing. `web/tests/living.test.ts` (18 → 22): a break rests, time off draws nobody, waiting never looks like work, overflow desks are not one pixel, and occupancy counts non-ambient agents.
- **Known limits, stated.** Inside a *running* multi-step workflow the next step still starts regardless of working hours — the gate is on delegation, not on step start, for the architectural reasons above. Per-agent `workingDays` is stored and validated but still not editable in the UI, and there is no per-agent timezone. Calendar entries have no recurrence, so a daily break is one entry per day. There is still no UI to create a calendar entry.

## 25. Organisational memory, the Manager's history, and operational notices (2026-09-18, as built)

Three audits first. The decisive finding: **almost all of this was already derivable**, and one thing was already written but private. `readMissionIn` reconstructs a whole mission — objective, status, agents, classified failure reasons, review verdict, recovery rounds, deliverables — and was module-private to the mission route. So Stage 9 **exports that reader and composes it**, rather than growing a second one that could disagree with it.

- **No history table, no projection.** Organisational history (`src/api/organisationHistory.ts`) is a READ MODEL: every record is composed on demand from authoritative rows and the immutable event log. There is nothing to rebuild, nothing to fall out of step, and deleting the file would lose no fact. The brief's four-way split is now structural: STATE is `agentState.ts`, HISTORY is this module, EXPLANATION is the Keeper, ACTION is the governed capabilities.
- **The one migration (0029).** `events` carried five correlation columns and was indexed on none of them, so every per-goal read — the mission trace, the Keeper, history — was a sequential scan. A partial index on `(goal_id, global_seq)`, matching the style of the existing run index. It changes no row and no history.
- **Bounded by construction.** Every entry point takes a window and limit, both clamped (`WINDOW`: 7 days default, 30 max; 20 records default, 50 max). There is no "everything since the beginning" query and no free-text filter — relevance is a fixed chain of keys. Postgres stays authoritative: no embeddings, no vector store.
- **Facts, not bodies.** History returns ids, hashes, statuses, reason codes and the short texts the runtime itself stamped. It never returns an artifact's content. A caller who wants a prior deliverable's words asks for the artifact by id, and it arrives through the Context Compiler **fenced as untrusted** — which is what makes "model prose never silently becomes fact" true by construction rather than by policy. Proven by a test that forges a deliverable claiming `status: completed` and demanding capabilities: history still reports the run as failed, and the forged sentence never appears.
- **Recorded vs calculated.** Every record carries `basis`. A Run failed: recorded. A goal is overdue, a follow-up is still outstanding: calculated, from records and the clock. Absent evidence is reported as absent.
- **The Manager's history is a governed READ capability (Stage 10).** `manager.inspect_history`, its own Grant on the Manager, and a snapshot fixed in code — exactly `{ days: 7 }`, like the calendar read — so no model can widen the window, name another agent's history, or ask a question of its own. Refusal is tested for four malformed snapshots.
- **The budget was raised on purpose.** The plan's `maxRetrievedItems` was 2 and it passed exactly 2 artifacts. Adding history as a third would have **silently evicted the roster** as a `"budget"` exclusion and the Manager would have planned with no workforce. Raised to 3 (and input tokens 6,000 → 8,000), which is the difference between a feature and a quiet regression.
- **Notices are derived, never invented (Stage 11).** `src/api/operationalNotices.ts` maps runtime events to notices for the operator: a failed task (carrying the runtime's own recorded reason), a mission completed, failed or recovering, a meeting held or not held, a decision recorded, a follow-up started. A fifth 60-second sweep writes what is missing. **Idempotency is free**: the key is `<kind>:<eventId>:<recipient>` and the existing unique key plus `onConflictDoNothing` means re-deriving is a no-op — so there is **no watermark** to keep, rebuild or corrupt. One pass looks back at most `LOOKBACK_HOURS` (24) over at most `SCAN_LIMIT` (500) events.
- **One notice comes from the clock, not an event**: `goal_overdue`, written once per goal, and its words say plainly that being late is not a failure. The pending-approval notice was deliberately NOT moved here — `GET /workplace/notifications` already derives it live from the approvals, so it disappears when one is resolved and can never go stale. Two sources for one fact would be worse than one.
- **Priority is a static map applied at read time** (`NOTIFICATION_PRIORITY`). Nothing stored, nothing scored, no model, and no new column — the test asserts the table has none.
- **Audience is deterministic.** `operator` became a real stored recipient, matching the actor convention. No model output selects a recipient.
- **`markNotificationRead` existed and nothing called it.** The Calendar's notice list now has a Mark-read control and shows read state, plus provenance links to the meeting and the mission a notice came from.
- **Keeper.** A new `delay` intent answers "why is this late / not started / taking so long", citing the deadline, the unfinished workflow runs, the interpreter's one-step-at-a-time rule, and the diary — separating recorded from calculated, and saying "no deadline was set" rather than inventing one. It was first written too greedily and stole "why is X waiting?" from `policy`, which explains approval waits better; the regex was narrowed and both behaviours are now asserted.
- **Progression untouched.** Reading history, receiving notices and answering questions award nothing: `agent_xp_awards` still has one writer driven from `run_completed` events, and the tests assert no award whose rule mentions history, notices or waiting.
- **Tests.** 19 in `tests/api/organisationMemory.test.ts`: clamped windows, a mission recalled and an older one excluded, the runtime's own failure reason, overdue calculated from the clock, artifact ids and hashes with the body absent, one agent's history never containing another's, no writes and no model call, route clamping and refusal, notices written once and re-derivable for free, a failed task carrying the recorded reason, an overdue goal noticed once, unreadable events producing nothing, priority as a static map, notices granting nothing, the lookback bound, capability refusal for four bad snapshots, facts-not-bodies, and a forged artifact failing to become a fact.
- **Two things the invariants caught, not me.** The history adapter first lived in `capabilities/manager/`, which may not import the API layer — so it moved to its own capability directory beside `keepStats/`, and the Manager's plan now names only the contract, never the implementation. The rule was not weakened to fit the code. Separately, a Manager version holding no history Grant would have had its whole mission fail at the new position; an advisory READ must not become a hard dependency, so it is recorded as a skip with its reason instead — never silently, and never as though history had been consulted.
- **A latent test landmine, fixed.** The Stage 4 meeting tests scheduled meetings "now" without pinning `outsideWorkingHours`, so they passed in the afternoon and failed in the evening. They now set it explicitly: those tests are about meetings, not about office hours.
- **Known limits.** Meeting decisions still have **no id** — their identity is the meeting plus their index, and the duplicate guard compares text. Starting a follow-up is two transactions, so a Goal can exist with no `actions` entry if the second fails (the reverse cannot happen). Notices are addressed to the operator only; per-agent operational notices are not built. "Related recent missions" is deliberately narrow — the mission a decision started, or one a recovery followed — with nothing based on text similarity.

## 26. Command: phases, blockers, recovery and the mission timeline (2026-09-18, as built)

Audited first. Command and History were already well built; what was missing was that **the server knew more than the browser was told**, and two links pointed at nothing.

- **The trace IS the timeline.** `readMissionIn` already returned `trace[]` — the runtime's own recorded sequence over 24 event types, including `manager_recovery_started/decided`, `approval_required` and `run_failed`. It was rendered inside a collapsed `<details>` labelled "Trace", with the actor dropped. It is now a visible **Timeline**: each line keeps its recorded fact and gains the phase it belongs to (`PHASE_OF`) and a tone (`TRACE_TONES`) — both **fixed maps over event types**. No phase is computed from `workflowRuns[].steps` or anywhere else; the phase is read from the event. An agent actor is named; the runtime's own `system` actor is not noise worth showing. A mission with nothing recorded says so rather than hiding the section.
- **Three facts the server had and the browser could not see.** `MissionDetail` in `web/lib/api.ts` declared neither `recovery`, nor `goal.dueAt`/`goal.overdue`, nor the newly added `fromDecision` — so a recovered mission, a deadline and the decision a mission answers were all invisible however truthfully the runtime recorded them. All three are now typed and rendered: a due/overdue line that says **overdue is a time, not an outcome**; a Recovery block naming the round, the failure it answered and what the Manager decided; and a link back to the meeting whose decision started the mission.
- **The chain closes from both ends (Stage 13).** `fromDecision` was added to the mission response, sharing **one** query with the organisational history read model rather than duplicating it. Calendar already linked meeting → follow-up goal via `actions[].goalId`; History now links a mission's goal → `/command?goal=`, and only for goals in the Manager's own Project, because Command refuses anything else and a link to a refusal is worse than no link.
- **A dead link, fixed.** Command linked to `/history?q=<title>`, and History read **no URL parameters at all** — every such link landed on an unfiltered list. History now reads `?q=` and `?agent=` on mount. (The `/command?goal=` links emitted in Stage 11 were *not* broken: Command has read that param since it was written. I claimed otherwise before checking properly.)
- **Blockers rendered what they were not gated on.** The section was shown when `mission.blockers.length > 0` but iterated `mission.reasons` — two different fields for the same facts. It is now gated on the structured `reasons` it actually renders, and each reason links to the run it was read from. No new "blocker" vocabulary was invented: Stage 7 established this runtime has exactly one blocked state.
- **The mission list earns its two unused facts.** `blockers` (a count the API already returned and nothing rendered) and the new `overdue` now show on each row, so the operator sees what needs attention without opening anything.
- **A selected mission is shareable.** Command read `?goal=` on mount but never wrote the selection back, so a mission could not be linked to once you had clicked around. The URL now follows the selection.
- **Deliberately not built.** No CURRENT/RECENT/NEXT/ALERTS dashboard: Overview already answers CURRENT (who is where, approvals) and Calendar answers NEXT (meetings, entries). Adding a fourth surface would have duplicated both. No new endpoint and no new poll — everything rendered here was already on the wire.
- **A real inconsistency the suite caught.** The Keeper's "real activity or ambient?" answer read the MEETING clock, so outside 09:00–17:00 it said an idle agent was "not at work" — while `agentState.ts`, which reads the WORK clock, correctly said `available` (work outside hours is allowed by default). The Keeper now reads the same inputs as the state resolver, so the two can no longer disagree. This surfaced only because the suite happened to run in the evening.
- **Tests.** `web/tests/command.test.tsx` 12 → 16: the timeline with its phases and named actor, an empty timeline stating so, a deadline shown overdue while the mission still reads working, a recovery round with its failure and decision, and the link back to the originating meeting. `web/tests/historySettings.test.tsx` 8 → 10: a mission goal links to Command while an ordinary goal does not, and the `?q=` Command links with reaches the API as a filter.

## 27. Final acceptance: security, progression integrity, token accounting (2026-09-18, as built)

A verification and hardening pass, not a feature workstream. Three independent audits (security /
progression / token accounting) ran in parallel against the frozen architecture; the main agent
reconciled them, fixed what was real, and documented what was not worth changing. The permanent record
is `docs/architecture/TRUST_BOUNDARIES.md`.

**Two real defects, both of the same kind: a model's words getting more authority than they earned.**

- **Meetings were minting XP (Stage 15).** A meeting convenes as a Workflow Run with one Run per
  participant. Those Runs are non-loop, so they satisfied the success-sample rule, so every attendee
  earned task XP (100) plus the meeting's Workflow Run (250) plus its Goal (500) — **~850 each, per
  meeting**. The Manager schedules meetings autonomously, so it could have minted progression for the
  whole Keep by calling an all-hands. Fixed by declaring the two meeting Task kinds in
  `src/capabilities/progressionFacts.ts` as attendance rather than work; the projector filters those Runs
  out of `successes`, so one exclusion covers task, capability, workflow, mission, domain and achievement
  at once, and the projector still names no Task kind. **The existing test that claimed to cover this was
  a false positive** — it never convened the meeting, so no participant Run existed. It has been renamed
  to say what it actually checks, and a real test added that was verified to fail without the fix (9
  forged awards).
- **A Manager's brief could re-enter another agent's instruction channel unfenced (Stage 14).** `brief`
  and `completionCriteria` are model output, and their words can arrive inside a fence the Manager was
  reading. They were rendered verbatim into the worker's `invocationInstruction` — the runtime's own
  voice, last in the user message. Never an escalation (`validateTasks` re-runs against the live database,
  so no laundered text could add a tool, agent, Grant, budget or approval, or lift a stop), but enough to
  steer an already-granted tool and rewrite the finish condition. Fixed with
  `CompileContextInput.untrustedDirective` and `fenceDelegated`: the same unguessable per-compilation tag
  and the same untrusted-data policy as an artifact, with the trusted directive only pointing at it.

**Three false or misleading labels, corrected.** `keep_stats` described its subscription-token metric as
"primary model only" and listed secondary-model tokens as unrecorded — both untrue; the total includes
every entry the provider reported, and only the breakdown is missing. That label had already reached a
live Keeper report. `tokenReport`'s `unattributed` was documented as "the secondary model's share" when it
is really everything the provider did not attribute to the primary entry, which on some models includes
cached input. And `share.context` expresses an estimate against a measurement, which now says so.

**One honesty fix in the UI.** The Costs screen showed `sum(consumed_amount)` in usd as money consumed.
Every usd figure in this system is a client-side estimate — no provider has ever reported a usd cost. The
API now returns `consumedBasis` per unit, re-derived from the `budget_consumed` events that do record it,
and the screen says plainly when a figure was charged at estimate rather than measured.

**One latent defect closed by ordering, not by a check.** `persistDeliverableArtifact` spread the caller's
`extra` bag last, so it could have overwritten `basis`, `completion` or `format` — exactly the fields the
runtime vouches for — and one caller already puts sanitized model output in that bag. The spread moved
first, and a structural invariant now pins the order.

**Two fixes deliberately not made, and why.** Widening `cacheHit` so "the provider said nothing" stops
reading as "the provider said no cache read" is an API-type change reaching the event envelope and a
drift test, for a latent issue no adapter currently triggers — recorded as a known limitation instead.
Filtering estimated consumption out of `agent_performance.avg_cost` would change Model Router tier
preference during an acceptance pass; reported, not changed.

**The invariants did their job twice.** The structural rule that no tool `execute` runs inside a
transaction caught a raw `deps.db.execute` added for the costs basis query; the query was rewritten
through the query builder rather than the rule being weakened. The `capabilities/manager` import rule had
already forced the history adapter out in Stage 9.

**Acceptance.** 1263 backend tests pass (5 skipped: two QA harnesses gated on `QA_SERVE=1`, one CLI smoke
test gated on its env), 212 web tests, both typechecks, the production build. Browser QA at 1280 / 1440 /
1920 across 13 routes against a live API serving one of every truthful agent state: no horizontal
overflow, no console errors, no failed requests, no broken links. Every scenario in the runtime chain is
covered by deterministic tests, so **no live-runtime budget was spent** on this pass.

## 28. Provider usage truth: what was measured, and what was never said (2026-09-18, as built)

The `invocation_completed` payload now carries `usageAccounting` (`src/router/usageAccounting.ts`) — a
per-category record of provider-reported usage with an explicit `unknown[]` list. **No migration**: the
payload is jsonb and the six usage columns are untouched, because they are what the budget is reconciled
against and their meaning must not shift. Nothing here changes a counted amount, a reservation, a
resource unit or a route, and a structural invariant confines `buildUsageAccounting` to the three
provider adapters so a provider-measured-looking value cannot be manufactured from model output.

**The repo contained real recorded provider responses all along** (`benchmark/raw/phase2-results.json`,
16 live CLI runs). Three things were settled from that evidence rather than assumed:

- **Cache tokens are SEPARATE from `inputTokens`** — capture 1 reports `inputTokens: 10` beside
  `cacheCreationInputTokens: 7568`. This is the long-standing mystery of a 2-token `tokens_in`: the input
  was cached and reported in a field nobody read.
- **Thinking tokens are INSIDE `outputTokens`** — the CLI's own footprint figure sums input + output +
  cache and never adds thinking, and the top-level view shows 566 thinking tokens within an
  `output_tokens` of 967. Adding them would double-count, so `thinkingIncludedInOutput: true` is recorded.
- **A per-model entry is not always one call.** When the internal classifier runs on the same model as the
  request, the CLI merges both into one entry (1170/981 beside a top-level primary-only 10/967).
  `primary.mergedWithSecondary` records that disagreement. `secondary: []` therefore means "the CLI listed
  no second model", never "no secondary work happened".

**Cache semantics are opposite between providers, so the relationship is recorded, not the number alone.**
Anthropic reports cache reads separately from input; OpenAI reports `cached_tokens` as a SUBSET of
`prompt_tokens`. `cacheReadIncludedInInput` distinguishes them; flattening both into one figure would have
made them silently non-comparable.

**`unattributed` is null everywhere, deliberately.** Attributing a residual needs a provider-reported
total to subtract from. No provider gives one — the total the Keep charges is one it computes by summing
the entries, so subtracting those entries from it yields zero by construction. Writing a residual would be
arithmetic dressed as a measurement.

**Three wording defects, one of them mine.** A previous stage "corrected" `tokenReport`'s residual to
"everything the provider did not attribute to the primary entry, including cached input… not splittable".
**That was false.** `cost_amount` is Σ(input+output) over entries and nothing else, so the residual is
*exactly* the non-primary entries — and since this task, the per-model split is persisted too. Also
corrected: `events/types.ts` and the CLI adapter both claimed `secondaryUsage` was "recorded on the Event"
when `emitEvent` had always discarded it (the dead pass-through is now removed, and the split lives in the
payload); and `keep_stats` called its usd unknown "only pre-call estimates", when a usd figure is actually
provider-reported TOKENS at a local list rate.

**A unit-mixing bug in observability.** `tokenReport` computed `cost_amount − tokens_in − tokens_out`
unconditionally; for a `usd` run that subtracts tokens from dollars, and it then expressed a token
estimate as a percentage of the result. Now computed only for a token unit, and an unrecorded unit prints
as unknown instead of being labelled "tokens". `TRUST_BOUNDARIES.md` claimed unit separation was enforced
everywhere — true of the write and read paths, false by omission about observability. That omission is
closed.

**The entitlement question is still not answered, and the doc says so.** Recording cache and thinking
tokens narrows it from "how big might the gap be?" to "what multiplier applies to these now-visible
quantities?" — but whether they draw on the Max allowance is a fact about Anthropic's billing that no
response states. `subscription_tokens` remains a locally imposed discipline, not a mirror of entitlement.

**Tests.** `tests/router/usageAccounting.test.ts` (18) drives the real adapters — a faked CLI child, mocked
SDK clients — and persists each adapter's own result through the real `emitModelInvocationCompleted`;
nothing is hand-built and then declared correct. Verified to fail: making `reported()` return 0 instead of
null breaks 5 of them. Two structural invariants added: only a provider adapter may build the record, and
no governance, projection, workflow, execution or context module may read it.
